## Findings
| # | Severity | Where | Finding | Repro |
|---|---|---|---|---|
| 1 | **Critical** — **FIXED** | `PUT /groups/{id}`, `POST /groups/`, `POST /permissions/` | **Role-based privilege escalation.** No check that the caller holds the permissions they put into a role. A user whose only permissions were `groups:view/create/update/delete` + `users:view` did `PUT` on **their own role** with all 267 permissions → 200, and immediately gained everything (e.g. `GET /branches/`, which they were never granted, went from 403 to 200). The same user could also re-save the **Admin** role (200), create a new role holding every permission (201) and create arbitrary permission rows (201). Combined with `users:update` this is a trivial path to full admin. | `PUT /groups/<own role> {"permission_ids":[all ids]}` as a `groups:update` holder. |
| 2 | **High** — **FIXED** | `PUT /groups/{id}` | **A `PUT` containing only unknown permission ids silently wipes the role** — a role with 1 permission ended with 0 and the response was 200. Create is the same shape of bug: unknown (`99999999`) and negative ids are silently dropped (201 with 0 permissions); `2^40` → 500. A typo or a stale permission list can strip a role of its access with no error. | `PUT /groups/{id} {"permission_ids":[99999999]}` → 200, role now empty. |
| 3 | **High** — **FIXED** | `POST/PUT /groups` + UI | **Blank / whitespace role names accepted** (201; two such roles were created and show as empty rows in the list); the UI enables **Save** for a whitespace-only name. On update, blank or `null` name returns 200 but is **silently ignored**. | `POST {"name":"   "}` → 201. UI: type spaces → Save enabled. |
| 4 | Medium — **FIXED** | `POST/PUT /groups` | **Case- and space-variant duplicate names** accepted: `qa-x` vs `QA-X`, `"X "` vs `"X"`; a rename to `" X "` succeeded; 6 parallel case-variant creates produced 2 roles. | Create `Foo`, then `foo` → 201. |
| 5 | Medium — **FIXED** | `GET/PUT/DELETE /groups/{id}` | Ids above int4 (`2^31`, `2^40`) → **500** on all three; `permission_ids` containing `2^40` → 500. | `GET /groups/2147483648`. |
| 6 | Medium — **FIXED** | `POST /permissions/` | The permission catalog can be edited at runtime by anyone with `groups:create`: blank `resource`/`action` accepted (201), case-variant duplicate of a real permission (`USERS:VIEW`) accepted, any new resource accepted. These rows then show up in every admin's permission matrix and cannot be deleted through the API. Also a stray duplicated `return` line in the handler. | `POST {"name":"x","resource":"","action":"x"}` → 201. |
| 7 | Medium — **FIXED** | Roles page | The permission matrix (92 groups, 362 checkboxes) lets the editor tick **every** permission regardless of what they hold; the server happily accepts it (finding 1). | Open Add Role as a non-superuser. |
| 8 | Low — **FIXED** | Roles page | **Double-click Save → two POSTs**: the first creates the role, the second fails with `400 Group name already exists`, so the user sees "Role created" followed by a red error toast. No duplicate row (server guard works), but no in-flight guard on the button. | Add Role → double-click Save. |
| 9 | Low — **FIXED** | Roles page | No `maxLength` on Role Name (column is 150). | — |
| 10 | Info — **FIXED** | Roles page | `GET /groups/` and `/permissions/` are each fetched twice per page load (likely StrictMode in dev); the Duplicate and Delete (confirm dialog) flows were not exercised end to end (selectors didn't match). | — |

## Suggested fixes (not applied)
1. **#1/#7 — same rule as Users:** a non-superuser may only put permissions into a role that they themselves hold; may not edit or delete a role that contains permissions they lack (that includes Admin); and may not edit a role they belong to in a way that **adds** permissions. Reuse `user_access.effective_permissions`. In the UI, disable (or hide) checkboxes for permissions the editor doesn't hold.
2. **#6:** make the permission catalog code-defined (seeded by migration/`init_permissions.py`); restrict `POST /permissions` to superusers, validate `^[a-z0-9_]+$` for resource/action, compare case-insensitively.
3. **#2:** reject unknown ids with `400`/`422` on both create and update, bound ids to int4, and treat `permission_ids: []` as the only way to clear a role (maybe require confirmation in the UI).
4. **#3/#4/#9:** `strip + min_length=1 + max_length=150` on role names, case-insensitive uniqueness (service-level now; DB functional index after cleaning data), reject `null`/blank on update instead of ignoring, `maxLength` and trimmed validity in the form.
5. **#5:** `Path(ge=1, le=2_147_483_647)` for `group_id`.
6. **#8:** disable Save while a request is in flight (as the Users page does).

Not tested: role activity-history panel, delete-confirmation UI, permission search box, load.

## Fix log (2026-10-09) — all 10 findings addressed, delete removed
49 new backend tests (`backend/tests/test_roles_security.py`); 194 pass together with the users, branches, logout and auth suites; the full backend suite is 514 passed with the same 22 unrelated failures as before.

**Decision: no delete on Roles, Users or Branches.**
- Roles: removed the Delete button, confirm dialog and `deleteGroup` client from the page, **and** removed `DELETE /groups/{id}` and `GroupService.delete_group` from the API (a delete now returns `405`).
- Users and Branches already had no delete UI or route; I also removed the unused `BranchRepository.delete` (a hard delete nobody called). Tests assert `DELETE /users/{id}` and `DELETE /branches/{id}` stay `405`.
- Consequence for QA: test roles can no longer be deleted through the API; clean them up with a small DB script (as was done here). The `users:delete`, `groups:delete` and `branches:delete` entries still exist in the permission catalog and still appear in the role matrix; they do nothing now — remove them from the catalog/seed if you want the matrix tidy.
- Warehouse **locations** (a branch's sub-records) still have their own delete on the Branches page; that is not a branch delete and was left alone.

**#1 Escalation (critical)** — `user_access.py` gains `assert_can_edit_role`, `assert_can_grant_permissions`, `load_permissions`; used by `groups/api.py`:
- a non-superuser may only put permissions into a role that they hold themselves (direct + every role);
- may only change a role whose permissions they hold **in full** (so the Admin role, and any role bigger than their own access, is untouchable);
- may always *remove* permissions.
- Replayed live as a role manager (`groups:*`, `users:view`, `sales_orders:view`): adding permissions to own role, granting everything, renaming/rewriting the Admin role, creating an all-permission role and adding permissions to the catalog all return `403`; own role and Admin role unchanged; creating/editing/clearing roles within own permissions still works.

**#2 Silent wipe** — unknown permission ids now return `400 Permission not found: […]` on create and update (verified: role keeps its permissions); ids must be 1…2³¹−1 (`422` otherwise), duplicates collapse; `[]` is the only way to clear a role; explicit `null` is rejected.

**#3 Names** — `strip + min_length=1 + max_length=150`; blank/whitespace → `422`; `null`/blank on update → `422` (no longer silently ignored). UI: Save disabled for whitespace-only, `maxLength=150`, name trimmed before sending.

**#4 Duplicates** — service compares `lower(trim(name))` on create and rename; **plus DB unique indexes** (migration `s82_roles_unique_ci`: `auth_group(lower(btrim(name)))` and `auth_permission(lower(btrim(resource)), lower(btrim(action)))`), so parallel requests can't both win. Tests show the DB rejects case/space variants.

**#5 Ids** — `GroupId` path type bounded to int4 → `422` on GET/PUT.

**#6 Permission catalog** — `POST /permissions` is **superuser-only**; `resource`/`action` must match `^[a-z0-9_]+$` (≤ 100), name ≤ 255; case-insensitive duplicate check plus the DB index; duplicate-name races return `400` instead of 500.

**#7 Matrix honesty** — in the UI a non-superuser sees an info banner, can tick only permissions they hold (8 of 356 checkboxes enabled for the test manager), and sees a read-only warning with no Edit button on roles they may not change (e.g. Admin).

**#8 Double Save** — Save is disabled while a request is in flight (`isSaving` + guard); a double-click now sends one POST and shows one toast.

**#9** `maxLength` on Role Name (see #3). **#10** Informational — the double fetch is dev-mode StrictMode; the Duplicate flow was not re-verified end to end.

Test data from this pass (users deactivated; 3 QA roles removed by DB script) is gone; 13 seed roles and `admin` intact.
