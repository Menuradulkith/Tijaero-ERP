# Load test — 2026-10-09

Scope: list/search/paging endpoints of Users, Branches, Roles, Product Catalogs (products/categories/brands), Suppliers, Customers, Purchase Orders, PO/Quotation approvals, Quotations, plus creates (customer, supplier, category).

Setup: throwaway copy of the dev DB (`erp_load` on the dev Postgres container, dropped afterwards); a second backend on port 8030 (1 uvicorn worker, same code, login/route rate limit disabled for that process only via a launcher script, no repo change). Python asyncio + httpx, closed loop with 150 ms think time, one admin token, weighted mix (about 90 % reads, 10 % creates), 30 s per step. Dev DB and dev backend untouched. Data volume is small (about 13 quotes, handful of products), so this measures per-request overhead and concurrency, not big-table query cost.

| Virtual users | Requests | Throughput | p50 | p95 | p99 | 5xx |
|---|---|---|---|---|---|---|
| 5 | 638 | 21 rps | 67 ms | 274 ms | 351 ms | 0 |
| 25 | 1119 | **37 rps (peak)** | 524 ms | 939 ms | 1.0 s | 0 |
| 50 | 678 | 22 rps | 2.0 s | 3.3 s | 3.6 s | 0 |
| 100 | 100 | 3 rps | 32 s | 33 s | 33 s | **40 %** (500) |

Login burst: 10 parallel logins p95 0.63 s, 30 parallel p95 1.2 s (bcrypt), all 200.
Every endpoint behaves the same (no single slow page): at 25 users all p50 sit at 380–700 ms; slowest are `approvals/pending` and `approvals/statistics`, `quotes list`. Creates (customer, supplier, category) were all 201 with no duplicates/errors up to 50 users. No 4xx on any read.

## Findings

| # | Finding | Severity |
|---|---|---|
| 1 | **Collapse at 100 users.** Requests wait on the DB pool (`QueuePool limit of size 10 overflow 20 reached, timeout 30`) and return 500 after 30 s (40 of 100 requests). Cause: each request holds a connection for its whole life while the single worker is saturated, so waiting requests also hold connections. | High |
| 2 | **Per-request fixed cost is about 50 ms even on tiny lists** (1 user, `/customers/paged` 46 ms, `/groups/` 71 ms, `/common/approvals/pending` 92 ms). About 27 ms of that is `get_current_user` in `app/auth/dependencies.py`: it reloads the user with branches, groups, group permissions and direct permissions (4 queries, 267 permission rows for admin) on every request. That caps one worker at about 35 rps. | High |
| 3 | Throughput **drops** past about 25 users (37 rps to 22 rps) instead of plateauing; queueing plus pool contention. | Medium |
| 4 | `approvals/pending` and `approvals/statistics` are the slowest endpoints at every load (92 ms single user). | Low |

## Suggested fixes (not applied)
1. Cache the authenticated user's permission set and branch list for a short time (30–60 s, keyed by user id plus the token jti or a user version stamp) or load permissions lazily only when a route needs them; skip the `is_revoked` query with a small in-memory cache.
2. Release the DB session before slow non-DB work, raise `pool_size`/`max_overflow` to match the worker thread count, and lower the pool `timeout` (fail fast with 503 instead of holding 30 s).
3. Run more than one uvicorn worker (or gunicorn with uvicorn workers) in production; re-run this test after each change. The login rate limit is in-memory per process and would need a shared store with several workers.
4. Look at the two approval endpoints' queries once the table is large.

Not covered: large-table query cost (seed 10k+ rows and re-run), writes of quotations and POs, reports/exports, file uploads, multiple workers.
Script: `load_test.py` in the session scratchpad (not committed).

## Fix log (2026-10-09)
Re-run on a fresh scratch copy (same script, single worker):

| Users | Before | After |
|---|---|---|
| 5 | 21 rps, p95 274 ms | 24 rps, p95 205 ms |
| 25 | 37 rps, p95 939 ms | 60 rps, p95 535 ms |
| 50 | 22 rps, p95 3.3 s | **66 rps**, p95 814 ms |
| 100 | 3 rps, 40 % 500 errors | **63 rps**, p95 1.7 s, **0 errors** |

- **#2 per-request cost:** `app/auth/user_cache.py` keeps the loaded user (branches, groups, permissions) for 15 s, merged into each request session without queries. Any flush touching a User, Group or Permission empties the cache at once (role change, deactivation, password change take effect immediately in-process; with several workers the 15 s TTL bounds staleness). A per-user lock stops a stampede when the entry expires. Token revocation (logout) is still checked in the DB on every request. Tests: `tests/test_user_cache.py`; the suite clears the cache per test.
- **#1/#3 collapse:** three causes found by re-testing: (a) `get_db` teardown ran on the saturated thread pool, so finished requests kept their connection (now `async def get_db`); (b) more in-flight requests than pooled connections (new `app/core/admission.py` caps in-flight requests at 32 against 40 connections, extra requests wait up to 15 s, then a clean 503 with Retry-After); (c) the cache refill used a second connection (now the request's own). Pool is 20 + 20 with a 10 s timeout, and pool exhaustion is mapped to 503 instead of 500.
- **#4 approvals:** `/common/approvals/pending` did one branch lookup per row and `/statistics` one count per approval type; now two batched queries and one grouped query (`filter_visible_approvals`).
- Still true: one worker caps at about 65 rps. For production run several workers (gunicorn + uvicorn workers); the in-memory login rate limit and the user cache are per process, so move the rate limit to a shared store at the same time.
- Full backend suite: 1005 passed, 2 failed (the two supplier-advance cashbook tests, missing `fn_insert_cashbook_entry` in the dev DB).

## Post-fix verification (2026-10-09)

- Scripts: no 5xx anywhere; validation, duplicate-race, cross-branch (403), maker-checker, approve-race (1×200) and approval-gate results are identical to the earlier green pass (only the approver's user id differs).
